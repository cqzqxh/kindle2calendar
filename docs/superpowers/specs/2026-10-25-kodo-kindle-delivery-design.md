# Kodo 图片发布与 Kindle 定时拉取详细设计

日期：2026-10-25。状态：设计完成，待实现与联调。现有代码以 `088ed9c` 为核对基线；本文中的新增模块、命令选项和配置项均为拟实现接口。

本文细化 [ARCHITECTURE.md](../../../ARCHITECTURE.md) 的发布与设备协议。主流程图、日历来源及天气规则沿用该文档；显示布局沿用 [DESIGN.md](../../../DESIGN.md)。

## 1. 目标、范围与现状

完成“已生成的日历 PNG → Kodo 私有空间 → Kindle 定时下载并显示”。首版服务一个屏幕，默认每 30 分钟生成一次、每 30 分钟下载一次，使用 Wi-Fi 和 USB 供电。

| 能力 | 当前已有 | 本次设计补充 |
| --- | --- | --- |
| 图片生成 | Pillow 输出 1072 × 1448、16 级灰度 PNG | 生成标识、发布前完整校验 |
| Kodo 发布 | 尚无代码 | 历史版本、固定入口覆盖、读回验证、失败恢复 |
| Kindle 下载 | `run.sh` 循环下载、PNG 文件头检查、内容比较、FBInk 绘屏 | 尺寸与实际大小检查、单次模式、启动重绘、运行管理 |
| 失败恢复 | 下载失败保留本地图片，绘屏失败尝试恢复 | 明确保存失败、首次运行、异常退出、云端结果不确定的行为 |
| 定时任务 | 尚无工作流 | 约束调度、并发、超时和启用条件 |

钉钉读取和自动天气查询作为上游接入独立实现。发布模块接收已经完整生成的图片，无法从 PNG 判断来源是否漏页；来源完整性必须由上游保证，读取失败时不得调用发布。完整成功的空日历允许发布。

第一阶段可用明确的空日历或经同意的演示数据，手动验证上传和实机显示；完成来源接入后才启用自动生成与发布。设备拉取不依赖钉钉接入进度。

## 2. 固定决策

- 使用七牛托管 Runner 和专用私有 Kodo Bucket，不增加常驻云主机、管理服务或业务数据库。
- 设备只读取固定对象 `latest.png`，历史版本供发布校验和排障使用。
- 只允许一个发布者写同一个屏幕的对象前缀。生产任务统一经同一个 Actions 工作流执行；本地联调使用独立 `SCREEN_ID`。需要手动修复生产对象时，先暂停调度并确认没有在途发布。
- 下载使用带到期时间的完整 HTTPS 私有签名 URL；建议有效期 30 天，手动续期。实际允许期限和域名鉴权配置须联调确认。
- 首版 Kindle 每轮完整 GET 图片，再用 `cmp` 判断是否变化，便于复用现有脚本。每张图片最多 2 MiB。

下载方式的取舍：

| 方式 | 收益与代价 | 决策 |
| --- | --- | --- |
| 完整 GET 后比较 | 只维护一个 URL，兼容现有 curl；每天约 48 次完整下载 | 首版采用 |
| 条件 GET | 可能节省流量；需验证 ETag、304、CDN 和设备 curl 行为 | 流量实测后再评估 |
| 版本清单加图片 | 可先比较版本；增加对象、请求和签名维护，需处理清单与图片不同步 | 首版不采用 |

按每张 2 MiB、每天约 48 轮计算，常规轮询下载量约为 96 MiB；失败重试和手动启动会增加请求次数。这不是实际图片大小或费用估算，实际流量按生成图片大小和设备运行次数记录。

## 3. 对象与图片协议

### 3.1 对象命名

```text
family-calendar/<screen-id>/latest.png
family-calendar/<screen-id>/history/<UTC-YYYY-MM-DD>/<run-id>-<attempt>.png
```

`SCREEN_ID` 使用 1–64 位小写字母、数字和连字符，首尾为字母或数字。`run-id` 仅允许字母、数字、连字符和下划线，最长 80 位；`attempt` 为正整数。所有字段在拼接 key 前校验，禁止路径分隔符和 `..`。

Actions 使用 `GITHUB_RUN_ID` 与 `GITHUB_RUN_ATTEMPT`。本地预览生成 `local-<UUID>`，attempt 为 1；后续上传时保留原值。历史目录日期取图片 `generated_at` 的 UTC 日期，不取上传机器的本地日期。

历史对象只允许新增；相同 key、相同内容的重试可视为已完成，相同 key、不同内容必须报冲突，不能覆盖。历史前缀设置 7 天生命周期，`latest.png` 不设自动过期。生命周期清理由 Kodo 执行，不能依赖临时 Runner 的磁盘。

### 3.2 PNG 内容与元数据

| 项目 | 约定 |
| --- | --- |
| 格式 | 单帧 PNG，1072 × 1448 |
| 像素 | Pillow `L` 模式，8 bit 灰度容器；像素值仅为 `0, 17, …, 255`，共 16 级 |
| 大小 | 大于 0 且不超过 2,097,152 字节 |
| HTTP 类型 | 上传声明 `image/png`，下载仍检查实际内容 |
| `calendar_schema` | PNG 文本元数据，固定为 `1` |
| `screen_id` | 发布目标屏幕；必须与本轮配置一致 |
| `generated_at` | 含微秒和 `Z` 的 UTC ISO 8601 时间，在渲染前固定 |
| `run_id` / `run_attempt` | 本次生成身份；attempt 在 PNG 中以十进制文本保存 |

渲染可见时间和元数据来自同一个 `now`：图上按 `TIMEZONE` 显示“更新于 HH:mm”，元数据保存它的 UTC 表示。上传和重试不得把旧图片的时间改成当前时间。

新增 `publication.py` 的 `build_artifact(png_bytes, context)` 负责写入元数据，再执行完整校验并计算最终文件 SHA-256。历史对象、latest 和读回比较使用完全相同的最终字节，不在两次上传之间重新编码 PNG。

`preview.py` 保持离线生成行为，新增可选 `--screen-id`，默认 `preview`，写入上述本地生成标识。上传预览图时显式配置相同的 `SCREEN_ID`。已有无元数据的预览图继续可查看，但发布入口拒绝它，提示重新生成；不得从文件修改时间猜测图片日期。

云端验证分两步：先用 Pillow 检查 PNG 结构，再重新打开并完整解码，检查尺寸、模式、帧数和灰度集合。仅检查前 8 字节不能替代完整验证。元数据中的屏幕、时间和生成身份也必须合法；图片时间超前当前可信 UTC 时间超过 5 分钟时拒绝发布并提示校时。

### 3.3 新旧版本判定

发布前读取并验证当前 latest，保存完整旧图字节及元数据。仅 HTTP 404 表示尚无旧图；鉴权、网络、解码、元数据缺失等错误均终止发布，不按首次发布处理。

| 当前 latest 与候选图的关系 | 行为 |
| --- | --- |
| latest 不存在 | 允许首次发布 |
| SHA-256 完全相同 | 验证对应历史对象存在且内容相同；缺失时补齐历史，再返回 `already_current` |
| 候选 `generated_at` 更晚 | 允许发布 |
| 候选 `generated_at` 更早 | 返回 `stale_rejected`，不写任何对象 |
| 时间相同但内容不同 | 返回 `version_conflict`，不猜测谁更新 |
| 同一 run-id / attempt 的候选内容不同 | 返回 `version_conflict`，要求重新生成新的执行身份 |

先检查屏幕、生成身份冲突和摘要，再比较时间；同一执行身份内容不同必须拒绝，即使它的时间更晚。run-id 和 attempt 用于辨识一次生成，不作为跨任务的新旧排序依据。整个生成和发布 Job 串行执行，每次 Job 真正开始后重新获取来源，不能将排队前的旧数据重新打时间戳后发布。

这套判定依赖单一发布者，不是分布式锁，也不能防止其他账号直接修改对象。

## 4. 云端模块与接口

以下为拟新增或修改的文件，不表示已经存在：

| 文件 | 职责 |
| --- | --- |
| `publication.py` | 图片标识与完整校验、版本比较、发布步骤及恢复状态；通过存储接口调用 I/O |
| `storage/__init__.py`、`storage/kodo.py` | Kodo 配置、上传凭证、私有读回、响应分类；屏蔽 SDK 细节 |
| `scripts/__init__.py`、`scripts/publish_calendar.py` | 接收图片路径，加载配置，调用发布流程，输出脱敏结果与退出码 |
| `scripts/sign_download_url.py` | 在可信电脑签发固定对象的设备下载 URL，保存到受限文件 |
| `preview.py` | 离线生成时附加发布元数据，保留已有日程和天气输入行为 |
| `kindle/run.sh`、`kindle/config.example.sh` | 扩展设备校验、单次执行、启动重绘及配置 |
| `kindle/control.sh` | 启动、状态检查、停止；不安装系统启动项 |
| `tests/test_publication.py`、`tests/test_kodo.py` | 发布顺序、幂等、异常结果、恢复和签名策略测试 |
| `tests/test_device.py`、`tests/test_preview.py` | 扩展设备边界与图片元数据测试 |

发布层的数据契约：

- `GenerationContext`：带时区的 `now`、`screen_id`、`run_id`、`run_attempt`；`generated_at` 必须由该 `now` 转为 UTC 得到，调用方以同一 `now` 渲染图片。
- `Artifact`：最终 `png_bytes`、`sha256`、`screen_id`、`generated_at`、`run_id`、`run_attempt`。
- `StoredImage`：经过验证的 Artifact，以及读取的对象 key。
- `PublishResult`：`status`、`history_key`、`latest_key`、`sha256`、`generated_at`、`recovery_status`；不包含 URL、token 或密钥。
- `read_image(key)`：返回 `StoredImage`；只有明确 404 返回不存在，其他情况抛出分类错误。
- `put_image(key, artifact, insert_only)`：上传指定字节，返回 key 和 Kodo 内容校验结果；结果不确定必须显式区分，不能当作未写入。
- `publish_artifact(artifact, storage)`：执行下节步骤，决定发布状态和恢复行为。

Kodo 使用官方 Python SDK 生成上传凭证、签名下载地址和内容校验值。SDK 与 HTTP 依赖版本在实现时选定、核实超时能力后固定，不在设计中编造已经验证的版本。SHA-256 是本项目读回摘要，不能拿它直接与 Kodo ETag 比较；Kodo 返回的 hash 使用对应官方算法核对。

### 4.1 配置

| 配置 | 来源 | 校验 / 默认值 |
| --- | --- | --- |
| `QINIU_ACCESS_KEY` / `QINIU_SECRET_KEY` | Actions Secrets；本地可信进程环境 | 必填；不写命令参数和日志 |
| `KODO_BUCKET` | Actions Variables | 必填，专用私有 Bucket |
| `KODO_DOMAIN` | Actions Variables | 必填，长期 HTTPS 域名；不带查询串、片段或用户信息 |
| `SCREEN_ID` | Actions Variables / 本地环境 | 必填，与图片元数据一致 |
| `TIMEZONE` | Actions Variables | 默认 `Asia/Shanghai`；非法时区终止生成 |
| run-id / attempt | Actions 上下文或本地生成上下文 | 写入图片后保持不变 |

上传凭证有效期设计为 1 小时，每次仅授权精确的 `bucket:key`，限制 PNG 和最大 2 MiB。历史上传设置 `insertOnly=1`；覆盖 latest 不设置仅新增限制。不使用前缀 scope 代替可覆盖凭证：七牛官方规则规定前缀 scope 不能覆盖上传。

部署身份须具备相应对象的新增、覆盖和私有下载签名能力；恢复同样需要覆盖权限。设备仅得到固定对象的下载 URL，不得到上传能力或 SK。签名 URL 可能包含 AK 标识，但它不是独立下发的云端密钥对。

### 4.2 拟提供的本地命令

以下命令在实现后使用；当前仓库不能直接执行新增入口。先激活 `.venv`，由可信环境提供云端配置：

```sh
python preview.py --screen-id demo-screen --output artifacts/calendar.png
python -m scripts.publish_calendar --image artifacts/calendar.png
python -m scripts.sign_download_url --expires-days 30 --output artifacts/kindle-download.txt
```

第一条不传日程时明确生成空日历，适用于链路联调；生产自动任务不能用它代替尚未接通的来源。`--image` 必填，发布入口不在缺图时生成空图。

签发工具直接调用官方签名方法，默认建议 30 天；URL 写入权限为 `0600` 的新文件，终端只显示文件位置和到期日。默认拒绝覆盖已有文件，续期先生成新文件再替换设备配置。临时输出放在已忽略的 `artifacts/` 下，配置完成后删除；签名续期不必重新上传图片。

## 5. 发布步骤、重试与恢复

### 5.1 成功路径

1. **校验候选图**：完整解码并检查标识、大小与屏幕一致性；失败不访问写接口。
2. **读取旧版**：通过设备使用的同一域名和对象路径读取 latest。云端使用本次临时生成的短期签名，不复用设备长期签名。保存旧字节，执行版本比较。
3. **上传历史图**：只新增对应 history key；成功后读回，核对字节摘要和图片协议。若对象已存在，读回一致即幂等完成，不同则报冲突。
4. **覆盖前复查**：重新读取 latest，确认它仍与第 2 步一致；首次发布确认仍为 404。发现变化则终止本次覆盖。复查不能代替单一发布者约束。
5. **覆盖 latest**：使用精确 key 凭证上传与历史对象完全一致的字节。
6. **读回 latest**：经固定域名和对象路径 GET，检查 HTTP、完整 PNG、SHA-256 和元数据。上传接口成功不等于发布成功。
7. **返回结果**：只有历史确认和 latest 读回均完成，才返回 `published`，写入脱敏任务摘要。

### 5.2 网络与总时间预算

- 云端连接超时 5 秒，下载单次总时间 30 秒，上传单次总时间 60 秒；底层 SDK / HTTP 适配必须实测兑现，不能只设置无人使用的配置字段。
- 暂时网络错误、HTTP 429 和可重试 5xx 最多尝试 3 次，间隔 2 秒、5 秒。合法 `Retry-After` 可在剩余任务预算内采用。鉴权错误、配置错误和输入校验错误立即失败。
- 上传超时或连接断开先查询目标对象，不直接认定上传失败。历史对象读回一致可继续；最新对象的不确定结果按下表处理。重试使用同一候选字节和生成身份。
- Actions Job 上限 10 分钟，包含安装依赖和来源读取。工作流最早脚本步骤记录一个 9 分钟内部截止时间，后续步骤共用，不能等到发布阶段才重新开始计时。正常发布阶段至多 480 秒，且必须在共享剩余预算中预留最多 90 秒恢复时间；覆盖前若连一次上传及恢复预算都不足，直接失败而不写 latest。按单调时钟核算，不让多层重试突破剩余预算；本地调用也设置总预算。
- 超时强杀、断电、Runner 丢失无法保证执行恢复代码。留下脱敏失败状态，由下一次任务重新读回判断；不宣称异常退出一定回滚。

### 5.3 失败结果

| 情况 | 动作与最终结果 |
| --- | --- |
| 校验、来源或旧图读取失败 | latest 不写入，任务失败 |
| 历史上传结果不确定 | 读回匹配可继续；无法确认或不匹配则失败，不覆盖 latest |
| 覆盖请求正常返回且读回匹配 | `published` |
| 覆盖请求结果不确定，但读回匹配 | `published`，同时记录该次写入经读回确认 |
| latest 读回始终为旧图 | 任务失败，记录 `previous_retained`；不把“上传返回成功”当作完成 |
| latest 写入后读回失败或内容异常 | 在单一发布者约束下，使用保存的旧字节尝试恢复并再次读回；整体仍失败 |
| 恢复前读到另一份有效版本 | 停止自动恢复，记录 `concurrent_change`，保留现场；不得覆盖另一发布者的内容 |
| 恢复成功 | `failed_restored`；报告失败与恢复完成 |
| 恢复也失败或读回仍不确定 | `failed_recovery_unverified`；明确云端当前内容未确认 |
| 首次发布失败，没有旧图 | `failed_no_previous`；不删除已可能写入的候选图，不声称回滚成功 |

发生覆盖失败后，恢复前尽可能再读当前对象；当前就是旧图则无需写回，当前为候选图可恢复旧图，出现第三个有效版本则停止恢复。读取始终失败时，仅在单一发布者已确保的前提下尝试恢复；不能证明恢复成功时必须报告未确认。

历史与 latest 不是跨对象事务。Kindle 可能在云端恢复前下载过一张候选图，也可能在云端发布成功后尚未拉取；云端不宣称设备已显示。首版没有设备回执服务。

### 5.4 缓存与最终可见性

首版使用专用、长期 HTTPS 源站域名，latest 读请求应直接得到对象内容。若实际接入 CDN，对 latest 配置不缓存，或经过联调确认的不超过 60 秒缓存；私有资源的缓存命中仍必须验证访问权限。

云端读回的临时签名可能与设备固定签名具有不同缓存键。因此联调必须使用**同一条设备签名 URL**连续读取两次发布，确认覆盖可见，不能只验证每次新签名的 URL。无法证明缓存行为符合预期时，不启用自动发布。

不在完整签名 URL 后追加随机数或时间戳。历史图可长缓存，但保留私有鉴权和 7 天对象生命周期。

## 6. Kindle 程序设计

### 6.1 文件与配置

```text
/mnt/us/family-calendar/
  run.sh                 # 单次同步和循环同步
  control.sh             # 启动、状态、停止
  config.sh              # 受限本地配置
  ca-bundle.crt
  fbink
  calendar.png           # 最近一次显示并保存成功的图片
  .running/              # 原子目录锁和本次运行临时文件
    pid
    started              # 进程启动标识，用于防止 PID 复用
    powerd.previous
    curl.conf
    next.png
  state                  # 最后结果与连续失败次数，不保存 URL
  run.log                # 有限大小的脱敏日志
```

| 配置 | 约定 |
| --- | --- |
| `CALENDAR_URL` | 完整 HTTPS 私有签名 URL；禁止引号、反斜杠、CR/LF 注入 curl 配置 |
| `URL_EXPIRES_AT` | 新增，Unix 秒数，必须与 URL 的 `e` 参数一致；展示时转为 UTC，仅作维护提醒 |
| `CA_CERT` / `FBINK` | 保留现有配置，启动时检查可读 / 可执行 |
| `INTERVAL` | 默认 `1800` 秒，整数且至少 60 秒 |

目录权限建议 `0700`，配置与运行状态 `0600`，`umask 077`。签名通过私有 curl 配置传递，不出现在命令行、日志或状态输出。修改 URL 后需要受控重启，首版不在每轮重新执行配置文件。

### 6.2 启动与单轮同步

1. 校验配置及所需命令，使用 `mkdir .running` 获取独占锁。目录存在时拒绝重复启动，不擅自删除；记录 PID 和设备上可验证的进程启动标识。
2. 保存原 `preventScreenSaver` 值，再设置为 1。循环模式先检查本地 `calendar.png`；如果存在且通过设备校验，尝试绘屏并记录本进程是否已知显示成功。启动重绘不要求网络可用。
3. 立即执行首轮下载；后续在每轮结束后等待 `INTERVAL` 秒。这是“轮询间隔加执行耗时”，不保证整点或严格 1800 秒到达。
4. 下载到同一文件系统的 `.running/next.png`；TLS 验证开启，不跟随重定向，不关闭证书校验。只接受 HTTP 200；204、重定向、401/403、404 等都不能进入绘屏。curl 失败后丢弃临时文件。
5. 连接超时 10 秒、单次总时间 40 秒。短暂网络失败和 5xx 最多尝试 2 次，中间等待 5 秒；401/403、404、图片非法和磁盘错误不在本轮反复重试。连续失败不让循环退出，下一轮继续。
6. 检查下载后实际文件大小不超过 2 MiB、PNG 签名和第一个 IHDR 的宽高、位深、颜色类型。要求 1072 × 1448、8 bit 灰度；通过 `od` 逐字节解析，避免主机端序差异。云端做完整像素与结构验证，设备依靠 FBInk 解码确认可显示，不能把 IHDR 检查描述为全量 PNG 校验。
7. 若下载内容等于 `calendar.png` 且本进程已知上次绘屏成功，跳过刷新。内容相同但启动重绘失败时仍尝试绘屏，避免只按文件相等而永久不显示。
8. 先使用 FBInk 显示新图；成功后再将临时文件原子 rename 为 `calendar.png`。失败按下节恢复。成功写入状态，并清理临时文件。

curl 的大小限制保留，并增加实际大小检查。安装验收要验证无 Content-Length 的响应同样能在传输中限制大小；若旧 curl 不支持这一能力，安装经过设备验证的 curl 后再验收，不仅依赖下载结束后的检查。下载前预留至少 6 MiB 可用空间；空间不足不开始下载。正常更新不依赖 PNG 元数据解析，也不向设备加入 Python。

图片每次生成都会更新顶部时间，通常也会改变字节，因此“相同图片不刷新”主要用于没有新发布的轮询，不能承诺所有日程不变时都免刷新。

### 6.3 本地失败和退出行为

| 情况 | 行为 |
| --- | --- |
| 下载失败、签名失效、非 PNG、尺寸错误 | 保留现有成功文件和画面，记录原因，下一轮继续 |
| FBInk 显示新图失败 | 不替换本地成功文件；存在旧图时尝试重绘，恢复也失败则记录 `restore_failed` |
| FBInk 成功但 rename 失败 | 视为未完成更新；保留旧文件并尝试重绘旧图，记录 `save_failed` |
| 首次运行无旧图且绘屏失败 | 记录 `no_previous`，下轮继续；不虚构可恢复图 |
| 首次运行绘屏成功但保存失败 | 显示状态标记未知，保留失败记录，下轮重试；不能记录为持久成功 |
| state / 日志写入失败 | 不删除已保存的图片；尽力向 stderr 输出类别，不让状态文件故障触发图片回滚 |
| 正常停止或 INT / TERM / HUP | 停止等待与后续下载，完成必要清理，恢复原屏保配置，释放本进程的锁 |
| 强杀 / 断电 | 不承诺执行清理；重新启动先处理残留锁，本地最后成功图片作为恢复来源 |

rename 只能保证同一文件系统下的文件替换，不等于断电持久化保证；是否需要设备支持的同步措施由断电验收结果决定。强杀后屏保设置可能仍被占用，恢复时使用保存的旧值，不写死恢复为 0。

### 6.4 运行管理和手动刷新

拟提供：

```sh
sh control.sh start
sh control.sh status
sh control.sh stop
sh run.sh --once
```

`start` 以后台方式启动循环并等待启动确认，返回成功必须代表进程活着且已持有锁。`status` 检查 PID、启动标识及对应脚本身份，输出是否运行、最后结果、最后成功时间、连续失败次数和配置的 URL 到期时间，不输出 URL。

`stop` 只有在 PID、启动标识和命令身份匹配时才发 TERM，有限等待退出，不默认使用 KILL。无法确认身份时返回明确错误，不能因为 PID 文件存在就杀进程。PW3 的 `/proc` 能力在安装验收时验证。

`--once` 只执行一轮，成功更新或确认相同且可显示返回 0；同步失败返回非零，随后清理锁并恢复屏保配置。一次性模式退出后不承诺长期保持日历画面，长期展示使用循环模式。若循环已运行，单次模式因锁占用失败；现场刷新采用“受控停止 → 单次运行 → 重新启动循环”，不同时启两个下载器。

锁残留时先核对运行状态和进程身份。无法确认则交由维护者处理；确认旧进程已不存在后，恢复保存的屏保值、移除残留临时文件和锁，再启动。首版不猜测固件版本、不自动安装开机启动项；重启后需手动启动，自动拉起作为实机环境明确后的独立工作。

## 7. Actions 接入与交付操作

生产工作流仍使用 `.github/workflows/calendar.yml`、`[qiniu, ubuntu-24.04]`、`7,37 * * * *` 和 `workflow_dispatch`，固定 concurrency group，`cancel-in-progress: false`，整个生成和发布 Job 限时 10 分钟。

生产 Job 顺序为：checkout → 安装固定依赖和字体 → 本次完整读取来源 → 生成带元数据图片 → 调用发布模块 → 输出脱敏结果。来源失败终止，天气失败由上游生成不可用天气区域；不能让预览脚本的缺省空输入掩盖接入失败。

当前日历来源未接通期间，只做明确标识的手动链路联调；不启用生成空日历的定时任务。生产 scheduler 启用条件是钉钉读取、Runner、Kodo 与设备四项分别验证通过。固定发布入口也供本地手动验证使用，但生产和测试使用不同 screen-id。

首次安装顺序：

1. 建立私有 Bucket 和长期 HTTPS 域名，配置历史前缀生命周期和 latest 缓存策略。
2. 设置可信发布身份、Secrets / Variables，完成一张演示图的发布和固定入口读回。
3. 在可信电脑签发设备 URL，记录到期日；通过受信任的设备配置通道写入 `config.sh`。
4. 在 Kindle 安装已验证的 FBInk、TLS curl 和 CA bundle，确认设备时间及剩余磁盘空间。
5. 执行单次下载验证，再启动循环。更新一张不同图，验证同一设备 URL 可以取得新内容。
6. 完成来源接入后启用云端调度，进行 48–72 小时连续运行验收。

URL 续期时先生成并验证新 URL，再受控停止设备程序、替换配置并重启；更换签名不更换对象 key。有效期不足 7 天时 `status` 和启动日志提醒维护者；这不是自动通知或自动续期服务。过期时只保留旧图，不能通过重试恢复授权。

## 8. 可观测性与退出码

云端结构化日志只保留阶段、对象 key、生成身份、摘要、状态、耗时和错误类别。设备记录请求状态类别、绘屏结果、最后成功时间和连续失败次数。禁止日程正文、图片内容、密钥、完整 URL、curl verbose 输出及包含 URL 的原始异常文本。

云端可报告 `published` 或 `already_current`，不能报告“Kindle 更新成功”。设备状态里的成功时间指本机同步 / 绘屏结果，图片顶部仍只显示生成时间。

云端 CLI 退出码约定：0 表示已验证发布或幂等完成，2 表示配置 / 图片输入非法，3 表示旧版本或身份冲突，4 表示发布失败且上一版已保留或恢复，5 表示首次失败或最终内容无法确认。详细原因从脱敏状态字段读取，所有非零退出均让 Actions 失败。

设备单次模式退出码：0 成功，1 同步 / 绘屏 / 保存失败，2 配置或依赖错误，3 锁占用。循环中的短暂同步失败更新状态并继续；配置与启动失败返回非零。

设备日志按 128 KiB 轮转，最多当前文件和一个旧文件；状态文件使用同目录临时文件再 rename，避免半写。首次无成功记录时显示“尚无成功同步”，不能把进程启动时间当作同步成功。

## 9. 验收用例

| 层级 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| 图片 | 错误尺寸、RGB、额外灰阶、截断 PNG、超大图、无元数据 | 发布入口拒绝，Kodo 不写入 |
| 图片 | 时间和时区转换、未来时间超限、屏幕不匹配 | 可见生成时间与元数据一致；非法输入拒绝 |
| 发布 | 首次发布 | history 与 latest 摘要一致，读回完成后才成功 |
| 发布 | 重复执行同一候选 | 幂等完成，不覆盖不同内容的历史对象 |
| 发布 | 旧图、同时间不同内容、同执行身份不同内容 | 拒绝覆盖，保留现有 latest |
| 发布 | 首次读取 latest 为 401/403/5xx、坏 PNG 或无元数据 | 不当作 404，不继续写入 |
| 发布 | 历史写入 / 读回失败 | latest 不更新 |
| 发布 | 上传已经成功但客户端超时 | 经读回确认真实结果，不误判、不中途换候选图 |
| 发布 | latest 读回失败、恢复成功 / 失败、首次无旧图 | 分别输出失败已恢复 / 未确认 / 无上一版，均非零退出 |
| 发布 | 覆盖前对象变化、恢复前出现第三个有效版本 | 停止覆盖或恢复，报告并发修改 |
| 发布 | 总时间预算耗尽 | 有限退出，不无限重试，不删除 latest |
| 缓存 | 连续发布两张图，复用同一设备签名 URL | 在约定缓存窗口内读到新图；过期与无签名请求被拒绝 |
| 设备 | 正常下载和内容相同 | 先绘屏后保存；已知成功且相同时跳过刷新 |
| 设备 | 重启、网络不可用但有缓存 | 启动时尝试显示本地缓存，持续重试网络 |
| 设备 | 204、302、401/403、404、HTML、损坏图、错误 IHDR | 不替换成功图片；失败原因可区分 |
| 设备 | FBInk 失败、恢复失败、rename 失败、磁盘不足 | 正确保留旧文件并记录结果；不误报成功 |
| 设备 | 多进程、残留锁、PID 被其他进程复用 | 不并行绘屏、不误杀、不自动删除不明锁 |
| 设备 | 正常退出、网络请求期间停止、强杀后恢复 | 正常退出恢复旧屏保值；异常残留可按文档处理 |
| 凭据 | 检查进程参数、日志、状态文件和失败输出 | 无完整签名 URL、SK 或日程正文 |
| 实机 | 连续运行 48–72 小时、跨天、断网恢复、签名过期 | 更新、缓存保留和失败恢复符合上述协议 |

单元测试使用假的存储客户端和假的设备命令，断言调用顺序和真实文件结果；增加可解码的有效 PNG 夹具及损坏 PNG 夹具，不能仅用“PNG 文件头加任意文本”证明校验正确。真实 Kodo 与 PW3 验收单独记录，不能用模拟测试替代。
